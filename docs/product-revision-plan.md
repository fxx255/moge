# 墨格 Moge · 交互调整与问题修复方案

日期：2026-10-02

状态：核心修改已实施，版本 0.2.0。完成情况、实际验证和待实机确认的事项见 [本次修改报告](revision-progress-report.md)。下文保留原方案作为范围与验收依据；排查假设不等于已确认根因。

范围补充：用户确认尚未开始实际使用，无需保留旧开发版数据。本轮取消旧数据库、旧题册和旧偏好的迁移工作；GitHub 分发与应用更新列为后续阶段。

本方案调整原 `implementation-plan.md` 中的取景优先、固定学科分类、语音输入和快捷追问设计。原 `progress-report.md` 保留为当时版本的完成记录，不能代表本次调整后的验收结果。

## 1. 整体方向

应用以“新对话”为首页，拍照成为对话输入的一种方式。历史对话自动保存；题册用于用户主动收藏、整理题目。继续使用方格纸与黑板主题，减少拍题和提问时的操作项。

主要入口：新对话、历史对话、我的题册、设置。建议历史与题册放在首页侧栏，设置通过侧栏或顶栏进入，避免额外挤占输入区。

## 2. 首页与拍照流程

- 启动进入空白新对话，展示简短提示和输入栏，不自动启动相机或申请相机权限。
- 输入栏保留文字、拍照、相册和发送。删除应用内麦克风入口与回答后的快捷追问卡片。
- 新对话可直接输入，也可先拍照或选图；只有首次发送时才生成正式历史记录，避免产生空会话。
- 拍照确认后，将照片放回原对话的待发附件区，可继续补充文字后发送。无论首问还是追问，都不因拍照额外创建会话。
- 拍照取消、查看历史后返回、切换设置等操作保留当前文字和待发附件。草稿不混入其他会话。
- 拍照确认页保留照片预览、裁剪、删除、继续添加和“使用照片”，不自动发送。

实现涉及 `MogeNavHost`、`SolveScreen`、`SolveViewModel`、`HomeScreen`、`ConfirmSheet` 和草稿/附件交接。相机页应成为独立的拍照路由，回传附件结果，复用已有解答页作为首页。

## 3. 同一对话多次生成图像

### 目标行为

同一会话的每次回答都能保存和显示自己的图像，不覆盖前轮图像。重新生成、自动续写、返回历史和重启应用后，图片位置与正文仍然对应。

当前代码的生成图像主要是函数图和框图。此次修复覆盖已有图形链路，不增加新的通用文生图接口。

### 排查与修复原则

1. 固定复现步骤：首轮画图；第二、第三轮再次要求画图；修改参数再画；同一规格重复画；一次回答包含多图；长回答自动续写。
2. 按回答消息和请求尝试记录解析出的图槽、渲染结果、文件路径、数据库写入与界面读取，定位在哪一环丢失。
3. 新回答的图编号从 1 开始；同一次回答的自动续写才进行编号偏移。检查历史中的插图标记是否诱导模型跨回答累计编号。
4. 每条回答使用自己的附件槽位，不从会话级“最后一组图”取图；失败槽位保留原编号。
5. 检查界面状态是否正确随消息、路径和文件修订刷新。正文分段只依赖文本和槽数属于合理缓存，不能仅凭这一点判定缺陷；图片解码与显示必须使用实际路径和必要的修订标识。
6. 检查相同图形规格的文件复用、写入并发，以及附件清理是否遗漏有效引用。现有内容哈希缓存可继续使用，不需要为所有重复图强制生成新文件。
7. 生成或解码失败时，在对应位置显示失败提示；可重试的本地问题不必再次调用模型。不能成功完成回答却静默漏图。

重点检查 `GenerationManager`（含 `GenerationFinalizer`）、`ReplyFigure`、`FigureImageStore`、`SolveItems`、`AnswerMarkdownBody`、`InlineFigure`、`AttachmentJanitor`。

## 4. 自定义分类与独立历史

### 历史对话

- 自动保存全部已发送的会话，按最近更新时间排列，支持搜索、打开继续提问、重命名、置顶和删除。
- 历史列表显示标题、最近内容、时间和可选缩略图，不要求先选学科。
- 保留当前生成保护、中断提示和重试机制，避免重构后无法找回未完成的回答。

### 我的题册

- 通过回答上的“收藏到题册”主动收录，默认收藏当前问题与对应解答；同一对话中的不同题可以分别收藏、分类。
- 分类由用户创建、改名、排序和删除，不预设数学、英语等学科，也不让模型直接决定归属。
- 首版每条收藏归一个分类，支持移动分类和“未分类”；“未分类”是未指定归属的状态，不是固定学科。
- 题册支持按分类查看与搜索；收藏可打开保存的内容，并在源会话仍存在时回到原对话。
- 收藏保留题目与解答的独立快照，包含照片、公式、图表及完整解答。重新生成源回答不静默改写已收藏内容，用户可主动更新。
- 删除分类只将收藏移至未分类；移出题册不删除历史。删除历史保留独立收藏，删除确认文案说明这一行为。

### 数据结构

- 将会话记录与题册条目分开，增加用户分类和收藏实体；收藏保存源问题/回答标识及内容快照。
- 按新结构直接设计数据库，不实现旧开发版的 Room 迁移、旧会话转收藏或旧学科转换。开发验收采用全新安装，不依赖兼容旧测试数据。
- 移除不再使用的固定学科字段和枚举；新题册仅使用用户分类。
- 停止模型学科结果对分类的直接写入；标题自动概括仍可保留。
- 扩展附件引用扫描：独立收藏中的照片和图表同样视为有效引用，不能在删除历史后被清理。
- 首次正式发布后，更新必须保留用户已经产生的对话、收藏和设置；不把清库升级作为长期更新策略。未来数据库结构变化的兼容工作按实际发布版本另行安排。

主要涉及数据库实体/DAO/仓库、历史页面、自定义分类页面、题册页面、回复中的收藏入口与 `AttachmentJanitor`。这是本轮数据结构变化最大的部分。

## 5. 模式精简与答案展开

### 模式入口

- 拍照页和照片确认页建议取消整组“详细解答 / 只要答案 / 帮我查错 / 举一反三”选择，将解题偏好集中到设置，拍照流程只处理图片。
- 删除“举一反三”预设及默认追加变式题的指令，设置中也移除该项。正常文字提问仍按用户实际请求处理。
- 设置保留“标准解答”和“检查我的解答”的生成偏好；将旧“只要答案”整合为下面的显示开关，避免出现没有讲解却提供展开按钮的冲突。
- 新安装默认使用标准解答、关闭答案优先，不处理旧开发版偏好或请求快照的迁移。新版本自身的中断恢复与重试继续保留。

### 新增“答案优先”开关

- 默认关闭，继续完整显示解答。开启后，解题结果先显示最终答案与“展开解答”。
- 模型仍生成并保存最终答案与完整讲解，点击展开读取本地已有内容，不再发起请求。这是显示方式调整，不承诺减少模型费用。
- 回复协议增加可选的独立答案字段；完整讲解继续保留。图槽由同一条回复统一管理，答案和讲解中的插图不能因拆分而丢失或重新编号。
- 不通过截取第一段或猜测标题来认定最终答案。普通聊天或缺少有效答案字段时，直接展示完整回复。
- 流式阶段先显示生成状态，获得可靠答案后展示答案卡；讲解未完成时标明进度，避免将部分文字当作最终答案。
- 展开状态按回答独立保存，页面重绘和旋转不反复收起；用户仍可手动收起。

### 稿纸视觉

答案区是简洁纸片，下方用轻微折边与“展开解答”提示。展开时解答纸从答案下方铺开，使用淡页边线和短暂高度动画，正文区域保持清晰。黑板主题使用相应配色；关闭系统动画时直接展开，大字号下按钮与内容正常换行。

涉及回复协议/解析、流式解码、持久化、设置、回答组件及导出。答案字段与分类/收藏实体统一纳入新数据库结构。

## 6. 横屏拍照与快门

- 竖屏继续使用上方取景、下方操作；横屏改为大面积取景区和侧边操作条，快门、闪光灯、相册及确认入口保持可见。
- 按可用窗口尺寸安排布局，兼顾横屏、小高度窗口和分屏，不能只是把纵向页面压扁。
- 快门改为圆形外环加实心圆，无“拍”字；提供“拍照”的无障碍描述和足够大的触控区域。
- 更新 CameraX 预览/拍摄方向，验证左右横屏、EXIF 转正、预览比例和裁剪坐标一致。仅声明 Activity 处理旋转不足以完成适配。
- 旋转时保留已拍照片和当前操作状态，避免重复绑定相机、预览黑屏和拍摄期间状态丢失。

横屏属于相机真机验收重点，需要用真实照片核对方向和裁剪，模拟器只覆盖布局与基础流程。

## 7. 长图片分享

### 导出范围与操作

- 回答上的“分享”进入图片预览，默认导出当前题目与该回答的完整解答，提供“保存图片”和系统图片分享。
- 题目包括用户文字、对应照片和已有识别文本；解答包括答案、讲解、公式、表格及生成图形。
- 用本轮问题与回答的关联确定导出范围。追问引用较早照片时，在预览中让用户确认关联题目，避免分享了其他题的照片或整段无关历史。
- 答案优先模式下仍默认导出完整解答，可选择仅导出题目与答案；分享结果不随屏幕当前折叠状态变化。
- “复制文字”可作为独立操作保留，分享主操作改为图片。

### 排版与实现

- 建立专用导出排版，使用清晰纸色、标题、页边距与题目/解答分区，不截取带输入栏和按钮的屏幕。
- 复用现有 Markdown、公式和图形渲染能力，确保长公式和宽表格完整导出；表格在导出中重新排版或适当缩放，不能只截取屏幕可见的几列。
- 默认使用适合传播的浅色纸面，确保黑板主题下也清楚；不带模型端点、密钥、调试信息或思考过程。
- 内容在生成完成后导出；历史中断内容需要明确标注，不把半截结果当成完整解答。
- 设定导出宽度与内存预算，分块排版/渲染。超出安全尺寸时分成连续图片并在预览中说明，避免创建单个超高 Bitmap 导致崩溃。
- 复用 `ImageExport` 的相册写入和 FileProvider 分享；增加多张图片出口及临时导出文件清理。

## 8. 删除语音与快捷追问

- 删除麦克风按钮、语音识别启动/监听/分段重启逻辑、录音权限申请和只为语音服务添加的声明。
- 删除“没看懂，再细一点”“换种方法”“出道类似题”“只看答案”等快捷追问卡片，腾出阅读空间；追问使用同一个文字输入栏。
- 用户仍可使用输入法自带的语音转文字，无需应用维护单独的识别流程。
- 清理对应资源、回调、测试及无障碍描述，避免隐藏按钮后残留权限申请。

## 9. 实施顺序

1. **多轮图像修复**：先固定复现样例和回归测试，定位并修复当前问题，避免后续页面重构掩盖原因。
2. **首页与输入简化**：切换新对话首页，拍照回传当前对话附件，删除语音、快捷追问和拍照模式条，完成横屏与圆形快门。
3. **数据与结果结构**：直接建立包含分类/收藏及答案字段的新结构，接通独立历史与自定义题册，更新附件清理引用，不做旧开发版数据迁移。
4. **答案稿纸展开**：接入设置开关、流式状态、独立答案与完整讲解，验证普通聊天及缺字段回复的回退行为。
5. **图片分享与整体回归**：完成专用长图排版、预览、保存/分享与超长内容分图，检查主题、字号、旋转和进程恢复。
6. **GitHub 分发与更新**：核心交互完成后，配置长期发布签名、GitHub 仓库、自动构建发布和应用内版本更新，见第 11 节。

每批完成相应检查再进入下一批；构建与测试结果写入新的完成记录，不直接沿用旧 P7/P8 报告中的结果。

## 10. 验收清单

- 冷启动进入新对话，未拍照时不申请相机权限；纯文字问答与图像问答都可完成。
- 当前对话追加拍照后仍在原会话中；取消拍照或旋转不丢草稿，空会话不污染历史。
- 同一会话连续三次生成图、同规格重复图、多图、自动续写和重新生成均显示正确；退出重进及重启后仍能查看。
- 图像失败有可见提示，编号不串位；清理附件不会删除历史、草稿、请求或收藏仍引用的文件。
- 可以建立任意名称分类、改名、排序、移动收藏；删除分类、删除历史、移出题册的行为符合上述规则。
- 全新安装后历史与题册为空，可创建对话、收藏和分类；重启后新版本自身的数据与中断状态正常恢复。
- 开启答案优先后，先显示可靠答案，展开无需第二次网络请求；普通聊天、缺答案字段和中断结果仍可阅读。
- 左右横屏拍摄方向正常，裁剪位置准确，操作区可用；快门为圆形，具有拍照无障碍描述。
- 分享图片含完整题目与解答，公式、宽表格和多张图没有漏项；超长内容在内存预算内导出，多张图片可保存/分享。
- 界面无应用内语音按钮、快捷追问和举一反三预设；黑板主题、大字号、关闭动画与进程恢复正常。

工程检查包括与变更相关的数据关系、消息/图槽关联、答案解析、导出排版及 Compose 操作测试，以及 debug/release 构建和 Lint。相机方向、系统图片分享和长图画质需进行设备实测。

## 11. 后续 GitHub 分发与应用更新

### 目标与当前状态

使用 GitHub 保存源码，通过 GitHub Actions 构建 APK，通过 GitHub Releases 分发版本。应用内检查新版本、展示更新内容、下载 APK，并交给 Android 系统安装器完成更新，首版无需自建更新服务器。

现已准备 GitHub 检查/标签发布工作流、专用签名配置和应用内更新模块，接入说明见 [GitHub 分发与应用更新](github-release.md)。尚未配置远程仓库与正式签名，当前本地 release 使用开发签名且关闭更新；没有创建仓库、上传源码或发布版本。

### 发布流程

1. 确定仓库名称与公开范围。首版建议采用公开 Releases，应用无需携带 GitHub 凭证即可检查和下载。若源码必须私有，应另设可公开访问的分发仓库或更新服务，不将长期访问令牌嵌入 APK。
2. 首次正式分发前配置专用、长期使用的发布签名。签名文件和密码不进入源码，GitHub Actions 通过 Secrets 取得签名材料；本地构建与 CI 使用同一发布身份。
3. 固定包名，递增 `versionCode`，使用 `versionName` 展示版本，并以发布标签（例如 `v0.2.0`）标识一次发布。调试包不接收正式渠道更新。
4. 普通推送/PR 运行测试与构建检查；发布标签触发测试、Lint 和签名 release 构建，全部通过后生成 Release。发布所需凭证仅用于可信的发布流程。
5. CI 显式配置 JDK 21、Android SDK 36 和 Build Tools 36.0.0，不依赖本机路径或本机离线缓存。首版沿用 arm64-v8a 正式包。
6. Release 包含固定命名的 APK、更新说明与机器可读的 `update.json`。元数据包含版本编号、版本名称、下载地址、文件大小、SHA-256、最低系统要求及包名，由实际 APK 信息生成，避免手工版本与产物不一致。
7. 发布正式版本时才让应用检测到更新，草稿和预发布不进入默认正式渠道。失败的构建不发布可见更新。

### 应用内更新流程

- 设置增加“关于与更新”，提供当前版本、手动检查更新、更新说明和 GitHub 项目入口。
- 应用启动时按时间间隔检查正式 Release，避免频繁请求；只在远端 `versionCode` 大于本地时提示升级。无网络或 GitHub 不可达不影响做题。
- 用户选择更新后在后台下载，显示进度，支持取消和失败重试；首版可先做手动触发下载，后续再提供仅 Wi-Fi 自动下载开关。
- 下载完成后校验文件摘要、包名、版本编号和签名身份，再使用 FileProvider/系统安装器安装。取消或失败可继续使用当前版本，不能将不完整文件交给安装器。
- 普通 Android 应用不能静默覆盖安装。“自动更新”指自动发现新版本与可选自动下载，最终安装需用户在系统界面确认；首次使用时按系统要求授权该应用安装来源。
- 首次正式版本至下一版本必须使用相同包名与兼容的签名身份，才能覆盖安装并保留应用数据。当前调试签名的开发包不纳入正式渠道覆盖兼容范围。
- GitHub 在部分网络中可能不可达，提供重试和打开发布页的出口；预留分发地址配置，必要时再增加镜像，不在首版额外维护更新服务器。

### 后续验收

- 标签发布可自动产出正确签名的 APK、更新元数据及 Release；CI 没有依赖本机特有配置。
- 同版本、低版本、预发布及不兼容包不触发正式升级；网络异常不阻塞日常使用。
- 更新说明、下载进度、失败重试、文件校验与系统安装流程可用。
- 用两次正式签名构建完成真实覆盖安装测试，新版本保留对话、分类、收藏、模型配置和设置。
