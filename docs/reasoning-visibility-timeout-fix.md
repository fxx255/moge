# 思考草稿可见性与慢模型等待修复

新提交和重试在准备时将活动状态置为 PREPARING。准备完成后，原实现只更新数据库为 RUNNING，内存活动状态仍是 PREPARING。解题页在没有正文时继续显示“正在读题”，而草稿组件只接收 STREAMING 状态，导致已经收到的 reasoning_content 无法显示，直到正文开始输出。

管理器现在在数据库成功进入 RUNNING 后同步更新活动状态，保留 requestId/attemptId 围栏。页面也将已有推理的活动回答视为流式回答，并允许准备态中的推理显示草稿，避免状态更新次序再次隐藏内容。两个主题均验证了先收到推理、展开草稿、追加推理、再收到正文的顺序。草稿沿用原有生成期间可见、默认折叠和不落库的行为；服务端尚未发送推理时无法显示其内容。

模型 HTTP 请求原来每次阻塞读取最多等待 180 秒。该限制包括等待响应头、首个响应字节和流中的无数据间隔，并不是整轮生成的总时间。长首 token 或代理缓存响应可能触发这一限制。现在连接超时仍为 10 秒，无数据读取上限为 10 分钟，每次 HTTP 调用另设 30 分钟总上限，防止仅有心跳的响应无限等待。模型列表查询单独使用 20 秒读取、30 秒总上限。文档分析已有的整轮 10 分钟限制继续生效。取消仍通过实际 Call.cancel() 立即打断阻塞读取；超时和 HTTP 503 不触发自动改协议重发。

使用用户提供的代理进行合成问题诊断，没有发送私人对话或题目，密钥只由诊断进程的环境变量读取。两个地址均能获取模型列表，实际模型 ID 为 cn:kimi-k3-1 和 cn:deepseek-v4.1-flash。

- HTTP 地址短题：KIMI 约 3.8 秒开始推理、10.2 秒开始正文、11.9 秒完成；DeepSeek 约 1.5 秒开始推理、2.1 秒完成。
- HTTPS 地址并行诊断中，一次 KIMI 请求返回 HTTP 503，错误码 no_healthy_account，属于代理上游可用性错误。
- HTTPS 单独复测应用完整固定协议、8192 输出上限及低思考设定：KIMI 约 8.6 秒开始响应、13.7 秒完成；DeepSeek 约 5.2 秒开始响应、10.7 秒完成。使用的本轮模式文本为合成详细解答指令。
- 与设置页相同的 KIMI ping/max_tokens=1 请求，两个地址均返回 HTTP 200，约 5.4 秒和 3.2 秒完成。

以上短题诊断没有复现用户长题的超时，不能据此断言用户当时的故障完全由 180 秒限制导致。进一步定位需要当时的等待时长、协议、联网开关和错误文字。代理的 503 或上游自身超时不能通过客户端延长等待解决。

定向检查 44 项通过，覆盖真实提交链在正文前发布推理、两个主题的可见与展开状态、延迟响应头与首个 token、停止等待、调用总超时及代理 503 不自动重发。后续完整回归 1101 项全部通过，lintDebug 与 assembleDebug 通过。完整验证结果保存在本机 release-output 中，诊断记录不包含密钥或响应正文。
